# AGENTS.md — правила работы ИИ-агента в этом репозитории

Этот файл — обязательная инструкция для любого ИИ-агента (opencode и др.), работающего с кодовой базой «Стакан». Человек-владелец пишет реализацию сам; агент владеет тестами, спеками, документацией и ревью.

## Иерархия источников правды

1. `spec.md` — скоуп, архитектура, контракты. Любое расхождение кода со спекой — либо баг, либо сначала правим спеку.
2. `docs/adr/` — архитектурные решения. Решение, противоречащее ADR, недопустимо без нового ADR.
3. `docs/specs/FEAT-*.md` — фича-спеки с acceptance criteria.
4. Код.

## Зоны ответственности

### Агент владеет (может создавать и править сам)

- `**/*_test.go`, `**/testdata/**` — unit, golden, integration (testcontainers), contract-тесты.
- `web/**/*.test.ts(x)`, `web/e2e/**` — Vitest, Playwright.
- `docs/**` — ADR, фича-спеки, changelog спеки.
- `.github/workflows/**` — CI.
- `db/migrations/**` — по описанию схемы от владельца (владелец описывает поля, агент пишет goose-файл с откатом).
- `Makefile`, линтер-конфиги — по запросу.
- Ревью PR: сверка с acceptance criteria, конвенциями, покрытием.

### Владелец владеет (агент НЕ правит без явного запроса)

- Весь код реализации: `cmd/**`, `pkg/**`, `internal/**` (кроме `*_test.go` и `testdata/`).
- `web/src/**` (кроме тестов).
- `api/openapi.yaml` — контракт фиксирует владелец; агент может предлагать правки через PR-ревью.

## Цикл разработки фичи (tests-first)

1. Владелец ставит задачу (issue/сообщение) со ссылкой на раздел `spec.md`.
2. Агент пишет `docs/specs/FEAT-xxx-<slug>.md`: acceptance criteria, контракты (REST/WS/события), edge cases, план тестов.
3. Агент пишет **падающие** тесты по критериям. Публичные интерфейсы при этом берутся из сигнатур, которые владелец фиксирует первым коммитом, либо согласуются в спеке фичи.
4. Владелец реализует до зелёного CI.
5. Агент ревьюит PR: критерии покрыты, конвенции соблюдены, `spec.md`/ADR обновлены при расхождениях.
6. Merge — только владельцем, squash, Conventional Commits.

## Команды (единственные точки входа)

```bash
make up                 # поднять инфраструктуру (docker compose)
make down
make test               # unit-тесты Go + Vitest
make test-integration   # testcontainers (PG/CH/Redis/Redpanda)
make lint               # golangci-lint + eslint + tsc
make migrate            # goose up
make gen                # oapi-codegen
make build              # go build ./... + vite build
```

Агент обязан после любых изменений прогонять `make lint` и `make test` (и `make test-integration`, если тронуты хранилища). Если команда падает по причинам вне зоны агента (код реализации) — агент описывает проблему, но не правит чужую зону.

## Конвенции кода (для тестов и ревью)

- Go 1.23+, `go.work`. Ошибки оборачиваются `fmt.Errorf("…: %w")`; паники запрещены вне `main`.
- Логи — JSON через `log/slog`; correlation id в контексте.
- Каждый сервис: `/healthz`, `/metrics`, graceful shutdown по `SIGTERM`.
- Канонические события — только по конверту из `spec.md` §4.5.
- Запросы к ClickHouse `md.*` — с `FINAL` или `GROUP BY`+`argMax(ver)` (см. §7.1 спеки).
- Миграции goose: `+ goose Up`/`+ goose Down` обязательны обе секции.
- Фронт: TypeScript strict; состояние — TanStack Query (серверное) и Zustand (клиентское).

## Тестовые конвенции

- Go: table-driven, `t.Parallel()` где возможно; golden-файлы в `testdata/`; флажок `-update` для перегенерации golden.
- Integration: testcontainers, тег `integration`, запуск только через `make test-integration`.
- Фикстуры бирж: сырые WS-сообщения записываются как есть, golden — ожидаемый canonical event.
- Фронт: Vitest co-located (`*.test.ts`), Playwright в `web/e2e/`.
- Целевое покрытие: rules engine ≥ 90%, нормализация коннекторов ≥ 90%, остальное — по критичности.

## Что агент делает проактивно

- Замечает расхождение кода и `spec.md` → флагает в ответе, предлагает правку спеки или issue.
- Видит архитектурное решение без ADR → предлагает черновик ADR.
- Падающий CI → диагностирует и докладывает, правит только свою зону.
